# Phase 1 구현 계획

> 상태: **승인됨 (2026-11-06).** 결정 1~5번은 추천대로 확정했고 `docs/architecture.md`에 기록했다.

**목표:** DOM → Virtual DOM 변환, Diff, Patch, State History와 검증 페이지를 구현한다.

**설계:** `docs/architecture.md` (구현의 기준 문서). 요구사항은 `docs/requirements.md`.

**도구:** Vanilla JavaScript(ES 모듈), Vite, Vitest, jsdom, jsdoc-to-markdown

## 공통 규칙
- 작업 브랜치는 `how-to-song`이다. `main`에서 직접 작업하지 않는다.
- 답변은 모두 한국어로 작성한다.
- 단위마다 테스트를 먼저 쓰고, 실패를 확인한 뒤 구현하고, `npm test` 통과를 확인한 뒤 다음으로 넘어간다.
- 화면을 바꾸는 단위는 브라우저에서도 확인한다.
- 단위가 끝날 때마다 핵심 로직과 설계 이유를 짧게 설명한다. 사용자가 직접 설명하고 발표할 수 있어야 한다.
- 설계와 다르게 구현해야 하면 멈추고 이유를 보고한다. 설계를 바꾸면 `docs/architecture.md`에 내용과 이유를 적는다.
- 요구사항에 없는 기능은 만들지 않고 제안만 한다.
- 실행하지 않은 동작은 "실행으로 확인 안 함"이라고 밝히고, 추측은 추측이라고 말한다.
- 테스트 실패와 건너뛴 단계는 있는 그대로 보고한다.
- 단위가 끝나면 검증과 `npm test` 통과를 확인한 뒤 확인받지 않고 작업 브랜치에 커밋하고 push한다. `Co-Authored-By` Claude 줄은 넣어도 된다.
- PR, 이슈와 보드 변경, 저장소 생성은 매번 먼저 확인받는다.
- 이슈를 닫는 키워드(`fix #번호`, `closes #번호`)는 쓰지 않는다.
- `src/` 파일 이름은 `_`로 시작하지 않는다.
- 내보내는 함수와 클래스에는 JSDoc을 쓴다. 설명은 한국어, 태그와 타입과 인자 이름은 영어로 둔다.
- 작업 분담은 `CLAUDE.md`를 따른다. `verifier`에게는 구현 과정을 설명하지 않고 검증 범위만 알려 준다.

## 사용자 확인이 필요한 결정
1. 이 계획 전체를 이대로 진행할지
2. `setProp` 추가: `createDom.js`에서 내보내고 `createDom`과 `patch`가 함께 쓴다. Phase 2의 `onClick`은 이 함수만 확장한다. 승인되면 `docs/architecture.md`에 기록한다.
3. `domToVdom`의 반환값: 제외 대상 노드는 `null`을 돌려주고 호출하는 쪽에서 걸러 낸다. 승인되면 `docs/architecture.md`에 기록한다.
4. `범위 밖` 추가 후보: `<pre>`의 첫 줄바꿈, `<template>` 요소. 둘 다 범위 밖으로 두기를 추천한다.
5. 요소 사이 공백(`<b>a</b> <i>b</i>`): 줄바꿈이 포함된 공백만 지우고 같은 줄의 공백은 유지하기를 추천한다. 단위 1을 시작하기 전에 확인한다.
6. 단위 1이 끝나면 Stop 훅 등록을 제안한다. 방법은 `docs/setup-docs-automation.md`에 있다.
7. 단위 7을 시작하기 전에 Playwright 도입 여부를 묻는다. 도입을 추천한다. 요구사항이 기능 테스트를 요구하고 Phase 2에서도 쓸 수 있기 때문이다.

## 사전 실행 결과
2026-11-06에 jsdom에서만 실행했다. 브라우저는 실행으로 확인 안 함.

| 입력 | 결과 | 대응 |
|---|---|---|
| `setAttribute('@click')`, `'1a'`, `'"foo'`, `'a"b'`, `'a<b'` | 오류 없음 | 단위 2에서 브라우저로 다시 확인 |
| `<a"b>`, `<div<>` 같은 태그 이름 | 파서가 받아들이고 `createElement`도 오류 없음 | 위와 동일 |
| `createElement('1a')` | `InvalidCharacterError` | 오류 시 기존 화면 유지 테스트의 입력으로 사용 |
| `<pre>\n\nabc</pre>` | 왕복하면 줄바꿈이 하나씩 사라짐 (`"\nabc"` → `"abc"`) | 고치지 않은 내용도 변경으로 잡혀 History에 저장될 수 있음 |
| `<template>` 요소 | `childNodes`가 0개 | 안의 내용이 조용히 사라짐 |
| 속성 이름 `__proto__` | `props[name] = value`로 넣으면 저장되지 않음 | `Object.fromEntries`로 `props`를 만듦 |
| 속성 이름 `constructor` | `'constructor' in {}`가 `true` | `Object.hasOwn`을 사용 |

## 검토 중점
1. 고치지 않은 내용으로 Patch를 누르면 변경 목록이 비어 History에 저장되지 않아야 한다.
2. 잘못된 태그나 속성 이름에서 오류가 나도 실제 영역과 History가 어긋나면 안 된다.
3. `constructor`, `__proto__` 같은 이름의 속성도 추가와 삭제가 맞게 동작해야 한다.
4. `textarea`를 비우고 Patch한 뒤 뒤로가기를 누르면 이전 내용이 복원되어야 한다.
5. 텍스트와 요소의 교체, 자식 수 변화, 속성 변경이 한 번에 일어나도 `path`가 어긋나면 안 된다.

## 단위

테스트는 `src/` 구조에 맞춰 `tests/core/`, `tests/phase1/`에 둔다.

### 단위 1. domToVdom
- 파일: `src/core/domToVdom.js`, `tests/core/domToVdom.test.js`
- 구현: `domToVdom(node)` → vnode 또는 `null`, `containerToVdom(container)` → 루트 노드
- `props`는 `Object.fromEntries`로 만든다.
- 테스트: 텍스트, 소문자 `type`, 속성 없는 요소의 `props: {}`, 중첩, 주석과 공백 제외, 텍스트 합치기(`a<!--x-->b` → `'ab'`), 최상위 요소 여러 개, 빈 영역, `__proto__`와 `constructor` 속성

### 단위 2. createDom
- 파일: `src/core/createDom.js`, `tests/core/createDom.test.js`
- 구현: `createDom(vnode)`, `renderRoot(container, root)`, `setProp(element, name, value)`
- `renderRoot`는 새 노드를 모두 만든 뒤 한 번에 교체한다. 중간에 오류가 나도 기존 화면이 유지된다.
- 테스트: Virtual DOM → DOM → Virtual DOM 왕복, 기존 내용 교체, 빈 루트, 오류 시 기존 내용 유지(`type: '1a'`), 잘못된 속성 이름
- 브라우저 콘솔에서도 `setAttribute`와 `createElement`를 확인한다.

### 단위 3. html.js
- 파일: `src/core/html.js`, `tests/core/html.test.js`
- 구현: `vdomToHtml(root)`, `htmlToVdom(html)`
- 테스트: 왕복 결과가 원본과 같은지, 이스케이프(`a &lt; b`, 속성의 따옴표), 최상위 `<tr>`, 닫지 않은 태그, 빈 문자열
- `diff`가 생기면 단위 4에서 왕복 후 빈 변경 목록도 확인한다.

### 단위 4. diff
- 파일: `src/core/diff.js`, `tests/core/diff.test.js`
- 구현: 공개 함수는 `diff(oldVdom, newVdom)` 그대로 두고, `path`는 내부 재귀 함수가 넘긴다.
- 노드 유무는 `undefined`로 판단한다. 빈 문자열도 텍스트이다.
- 속성 비교는 `Object.hasOwn`을 쓴다. `PROPS` 항목은 `set`과 `remove`를 항상 가진다.
- 테스트: 5가지 케이스, 판단 순서, 같은 입력의 빈 목록, `REPLACE` 시 자식 미비교, 속성과 자식의 동시 변경, 변경 목록 순서, 입력 불변, 내장 이름 속성의 삭제

### 단위 5. patch
- 파일: `src/core/patch.js`, `tests/core/patch.test.js`
- 구현: `patch(container, changes)`
- 테스트: `kind`별 동작, 빈 변경 목록, 여러 입력 쌍에서 Patch 후 `containerToVdom` 결과가 새 Virtual DOM과 같은지 확인
- "변경된 부분만 반영"의 증거로, 바뀌지 않은 노드가 같은 DOM 객체로 남는지 확인한다.

### 단위 6. StateHistory
- 파일: `src/phase1/StateHistory.js`, `tests/phase1/StateHistory.test.js`
- 구현: `push(vdom)`, `current()`, `back()`, `forward()`
- 테스트: 첫 상태 복귀, 양 끝에서 `null`을 돌려주고 포인터 유지, 뒤로 간 뒤 저장하면 앞 기록 삭제

### 단위 7. 검증 페이지
- 시작 전에 Playwright 도입 여부를 묻는다.
- 파일: `index.html`, `src/phase1/main.js`, `src/phase1/style.css`
- 동작은 `docs/architecture.md`의 `페이지 동작`을 따른다.
- 브라우저 시나리오: 로드, 수정 후 Patch, 변경 없는 Patch, 뒤로가기와 앞으로가기, 뒤로 간 뒤 새 Patch, 빈 입력
